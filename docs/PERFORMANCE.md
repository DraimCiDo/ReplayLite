# Производительность и расход ресурсов

## Требование продукта

Низкий расход ресурсов — один из основных критериев ReplayLite. Цель — сохранять повторы с минимальным влиянием на игру и выделяться эффективностью среди альтернатив. Это цель разработки, а не доказанное превосходство над всеми конкурентами. Производительность не оправдывает потерю кадров, звука, повреждение MP4 или потерю данных.

Сохраняйте аппаратный NVENC, передачу кадров на GPU, сжатые сегменты на диске и stream copy при экспорте. Отдельно оценивайте цену любой новой фоновой работы. Короткие анимации должны завершаться и прекращаться в скрытом окне. Восстановление должно иметь ограниченную частоту попыток; очередь, буфер, кеш и число процессов не должны расти без границы.

## До и после изменения

До изменения пути записи, экспорта, восстановления, таймеров или интерфейса снимите базовый результат на исходном коде. Затем повторите те же сценарии на новой сборке. Если исходную сборку получить нельзя, укажите отсутствие базы: абсолютный замер не подтверждает отсутствие регрессии.

В плане заранее укажите метрики и критерии: например, отсутствие активных таймеров анимаций после скрытия, ограниченный размер кольца, отсутствие устойчивого роста RAM и дескрипторов после повторных циклов. Численные бюджеты задавайте по сопоставимой базе, требованиям задачи и разбросу измерений; не придумывайте универсальный порог CPU или RAM для любого ПК.

Зафиксируйте Windows, CPU и число логических процессоров, GPU/драйвер, RAM, накопитель, версию/исходники приложения и FFmpeg, способ захвата, разрешение/поворот, FPS, битрейт, длительность буфера и аудиорежим. Сохраняйте одинаковую нагрузку и план питания. Отметьте прогрев, фоновые процессы, длительность и метод измерения.

| Сценарий | Что измерять и проверять |
| --- | --- |
| Открытое окно без записи | CPU/RAM, завершение анимаций, отсутствие бесконечной перерисовки |
| Трей без записи | CPU за достаточно длинный интервал, RAM, таймеры/hook; окно не должно продолжать анимации |
| Запись в трее | Приложение + FFmpeg: средний CPU, пиковая RAM, GPU VideoEncode/общий GPU/VRAM при наличии счётчиков, скорость записи на диск, размер кольца |
| Запись с открытым окном | Разница с треем при тех же параметрах и движении на экране |
| Экспорт во время записи | Время от команды до готового файла, пики ресурсов, непрерывность записи, отсутствие перекодирования |
| Повторные циклы и отказы | RAM/дескрипторы/потоки/процессы до и после прогрева; ограниченность повторов, отсутствие утечек и осиротевших процессов |
| Игра + запись | Одинаковая сцена/бенчмарк: средний FPS и 1% low либо frame time; сравнение с записью, выключенной в том же окружении |

Для записи измеряйте не меньше полного оборота выбранного буфера с запасом на прогрев; для поиска утечек — несколько циклов и достаточный интервал для проявления роста. Короткий smoke-тест не доказывает многочасовую стабильность. Для сравнения выполняйте не менее трёх сопоставимых прогонов и сохраняйте отдельные результаты, медиану и диапазон. При большом разбросе ищите причину до вывода.

CPU в процентах всех логических процессоров считайте как `100 * delta(CPU seconds) / elapsed seconds / logical processor count`, суммируя приложение и его дочерние процессы. Указывайте, если инструмент использует другую нормализацию. Не сравнивайте эти величины напрямую. Отличайте working set, private bytes и VRAM. VideoEncode не равен общей загрузке GPU, а короткая выборка Task Manager не равна среднему за тест. Нулевое приращение счётчика в коротком простое не означает нулевое потребление.

## Приёмка и регрессии

Если значение устойчиво ухудшилось сверх разброса базовых прогонов, исследуйте причину. Исправьте регрессию и повторите затронутые измерения. Не повышайте бюджет, не снижайте качество записи и не убирайте функциональную проверку, чтобы формально пройти приёмку. Если необходим компромисс, представьте пользователю конкретные результаты и варианты; независимые исправления продолжайте.

Нет доступа к GPU/счётчику/игровой сцене — отметьте соответствующую метрику как непроверенную. Нельзя заменять её соседней метрикой. Исторические значения в `VALIDATION.md`, `UI-VALIDATION.md` и README относятся к описанному там оборудованию и сценарию, а не к любой новой сборке.

## Сравнение с конкурентами

Для заявления о преимуществе нужны названия и версии сравниваемых программ, дата, одинаковые ПК, сцена, разрешение, FPS, кодек/профиль, сопоставимое качество и битрейт, аудио и длина повтора. Отдельно укажите различия функций и настроек, которые нельзя выровнять. Приложите результаты каждого прогона и проверку выходного видео.

Сравнивайте CPU, RAM, GPU/VRAM, диск, FPS/frame time и задержку сохранения; не выбирайте только выгодный показатель. Не запускайте конкурирующие рекордеры одновременно. Итог ограничьте проверенными программами, версиями и условиями. Без такого сравнения допустимо говорить о цели низкого расхода и собственных замерах, но не «самая быстрая» или «быстрее всех конкурентов».
