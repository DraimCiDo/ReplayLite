# Выпуск версии

После каждого завершённого набора изменений программы выпуск стабильного GitHub Release обязателен. Пользователь заранее разрешил повышение версии, коммит/push, новый тег и публикацию после успешных проверок, без повторного подтверждения. Включайте этот этап в план до реализации. Для правок только документации релиз не нужен, если не поручен отдельно.

Обычный push в `main` запускает сборку и проверку интерфейса, затем сохраняет EXE/ZIP как GitHub Actions artifact. Для публикации в Releases нужен тег версии.

1. Выберите новую `MAJOR.MINOR.PATCH`-версию, по умолчанию следующий PATCH. Если подходящий новый номер уже подготовлен для этих изменений и ещё не опубликован, используйте его. Обновите `VERSION` и датированную секцию `CHANGELOG.md`; историю предыдущих версий сохраняйте.
2. Соберите свежие EXE и пакет, проверьте номер во всех бинарных файлах, release notes и применимые сценарии по [TESTING.md](TESTING.md). В GitHub-hosted runner нет NVIDIA для проверки реального захвата. Версию фиксируйте до этих проверок.
3. Сделайте коммит и push. Убедитесь, что проверенная `main` содержит изменения и рабочая копия соответствует коммиту выпуска. Не выполняйте автоматический merge без разрешения и не ставьте тег на `main`, не содержащую изменения задачи.
4. Создайте и отправьте новый тег, совпадающий с `VERSION`, на проверенном коммите. Пример для уже подготовленной и проверенной `0.3.16` (не копируйте старый номер без проверки текущего состояния):

```powershell
git tag v0.3.16
git push origin v0.3.16
```

Workflow `.github/workflows/build-release.yml` проверит версию тега, загрузит зависимости с проверкой SHA256, соберёт и проверит EXE, создаст Portable ZIP и установщик Inno Setup из отдельных файлов, проверит реальную установку обоих режимов, откат/перезапуск обновления и создаст контрольные суммы. Публикация сначала создаёт draft, загружает файлы и только затем открывает релиз пользователям.

5. Дождитесь успешного завершения build и release jobs именно для отправленного тега. Проверьте GitHub Release: тег и целевой коммит совпадают с планом, `draft=false`, `prerelease=false`, версия выбрана Latest. Это важно для встроенной проверки обновлений через последний стабильный релиз.
6. Убедитесь, что доступны все четыре файла ниже. Скачайте опубликованные файлы и сверьте их SHA-256 с опубликованным `SHA256SUMS.txt`. Подписанные/собранные в CI бинарные файлы могут отличаться от локальных: проверяйте опубликованный комплект, а не требуйте совпадения с локальным EXE.
7. Дайте пользователю номер версии, прямую ссылку на Release и результат проверки CI/файлов. Только после этого доставка изменений программы завершена. Не ограничивайтесь сообщением «версия обновлена в Git».

`source/package.ps1` автоматически получает Inno Setup 7.1.0 в portable-режиме в `.deps-cache/`, без системной установки и изменения PATH. Перед запуском проверяются SHA-256 официального релиза и Authenticode издателя Pyrsys B.V. Сборка через самописный .NET-установщик больше не используется. Portable ZIP и формат обновлений сохранены.

Существующие теги и опубликованные релизы не перезаписываются. Если workflow упал, прочитайте лог и исправьте причину. Сбой окружения без изменения исходников допускает повторный запуск того же workflow. Если понадобилась правка исходников после создания тега, поднимите PATCH, пересоберите/проверьте и выпустите новый тег: повтор старого workflow не включает новые коммиты. Не используйте force push и не переносите тег. Если остался незавершённый draft, проверьте его целевой коммит, файлы и причину ошибки; не публикуйте неполный комплект.

Если нет необходимых доступов или CI недоступен, явно отметьте выпуск незавершённым и укажите, что необходимо для продолжения. Это внешняя блокировка, а не повод повторно спрашивать уже данное разрешение на выпуск. Один завершённый набор изменений программы — один релиз, без публикации промежуточных коммитов.

Текст релиза содержит только изменения соответствующей версии из CHANGELOG.md; генератор source/release-notes.ps1 не добавляет инструкции по установке и служебные сообщения.

Артефакты:

- `ReplayLite-Portable.zip` — вся переносимая папка приложения с portable.flag.
- `ReplayLite-Setup.exe` — установщик с выбором обычной установки или Portable.
- `ReplayLite.exe` — EXE для обновления уже распакованной папки.
- `SHA256SUMS.txt` — контрольные суммы трёх файлов.

Подключаемая подпись настраивается по [SIGNING.md](SIGNING.md); без аккаунта и сертификата текущая сборка остаётся неподписанной. Секреты пользователя не нужны: для публикации workflow использует встроенный `GITHUB_TOKEN` с `contents: write` только в job публикации.
