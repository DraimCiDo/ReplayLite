# Выпуск версии

Обычный push в `main` запускает сборку и проверку интерфейса, затем сохраняет EXE/ZIP как GitHub Actions artifact. Для публикации в Releases нужен тег версии.

1. Обновите `VERSION` в формате `MAJOR.MINOR.PATCH` и `CHANGELOG.md`.
2. Проверьте значимое поведение локально. В GitHub-hosted runner нет NVIDIA для проверки реального захвата.
3. Сделайте коммит и push.
4. Создайте и отправьте новый тег, совпадающий с `VERSION`:

```powershell
git tag v0.3.1
git push origin v0.3.1
```

Workflow `.github/workflows/build-release.yml` проверит версию тега, загрузит зависимости с проверкой SHA256, соберёт и проверит EXE, создаст Portable ZIP, встроит его в установщик, проверит установку/откат/перезапуск и создаст контрольные суммы. Публикация сначала создаёт draft, загружает файлы и только затем открывает релиз пользователям.

Существующие теги и релизы не перезаписываются. Если сборка упала, прочитайте лог, исправьте причину и повторите failed job; не используйте force push. Если осталось незавершённое draft-состояние релиза, сначала проверьте загруженные файлы и причину ошибки.

Артефакты:

- `ReplayLite-Portable.zip` — вся переносимая папка приложения с portable.flag.
- `ReplayLite-Setup.exe` — установщик с выбором обычной установки или Portable.
- `ReplayLite.exe` — EXE для обновления уже распакованной папки.
- `SHA256SUMS.txt` — контрольные суммы трёх файлов.

Сборка не подписывает EXE. Секреты пользователя не нужны: для публикации workflow использует встроенный `GITHUB_TOKEN` с `contents: write` только в job публикации.
