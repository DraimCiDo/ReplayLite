# Порядок работы агента

## 1. Подготовка и план

Прочитайте корневой `AGENTS.md` и инструкции в затронутых каталогах. Используйте `rg` для поиска конкретных символов, читайте нужные диапазоны. Не устанавливайте новые зависимости, если достаточно существующего toolchain.

До изменения файлов:

- Выполните `git status --short`, определите рабочую ветку и доступность `origin`. Сохраните чужие изменения. В папке без `.git` выполняйте доступную локальную работу и укажите ограничение.
- Найдите точки входа, владельцев состояния, фоновые процессы, таймеры, обработку ошибок и тесты затронутого поведения.
- Сформулируйте наблюдаемый результат пользователя, границы задачи и критерии приёмки. Для бага запишите шаги воспроизведения, ожидаемое и фактическое поведение.
- Создайте план по [шаблону](templates/WORK-PLAN.md). Для многошаговой задачи сохраните его в `docs/plans/<краткое-имя>.md`; для маленькой правки допустим план в сообщении с теми же полями. В файле не должно быть личных путей, записей экрана или секретов.
- Включите проверки успешного пути, ошибок, границ, повторных операций, восстановления, соседних функций и производительности. У каждого шага должны быть проверяемый результат и способ проверки.

Статусы шагов: `pending`, `in_progress`, `passed`, `failed`, `blocked`, `not_applicable`. `passed` ставится только после проверки. Для `blocked` укажите причину и необходимое действие; для `not_applicable` — почему сценарий не относится к изменению. Шаг реализации и шаг проверки учитывайте отдельно.

## 2. Исполнение

Работайте в порядке зависимостей плана. Параллельно можно выполнять независимые проверки, но нельзя отмечать зависимый шаг завершённым до его предпосылок. При изменении объёма сначала поправьте план. Не требуется повторное согласование обычных обратимых решений внутри задачи.

Меняйте минимальный необходимый участок. Сохраняйте пользовательские настройки, MP4, буфер при неудачном экспорте и корректное завершение дочерних процессов. При правках асинхронного кода проверяйте гонки сохранения, остановки, восстановления и выхода. Не скрывайте исключения ради зелёного теста.

Любое обнаруженное падение проверки разберите: код приложения, тест, окружение или устаревший артефакт. Сохраните исходный симптом. Баг продукта исправьте сразу в текущем цикле, добавьте регрессионную проверку, если она надёжно ловит причину. Не ослабляйте ожидания и не увеличивайте таймаут без объяснения. Для неустойчивого сбоя фиксируйте частоту и условия; один удачный повтор не доказывает исправление.

## 3. Проверки и исправления

Следуйте [матрице проверок](TESTING.md). После изменения исходников пересоберите EXE перед запуском тестов. Проверяйте код выхода исходного процесса, свежесть отчёта и реальные утверждения внутри теста. Не считайте код завершения фильтра логов результатом теста.

Цикл обязателен: воспроизведение → причина → исправление → проверка исходного сбоя → связанные регрессии → проверка [производительности](PERFORMANCE.md). Если среда не позволяет нужный тест, выполните независимые проверки и явно оставьте аппаратную или интерактивную часть незавершённой. Не выдумывайте результаты.

Сборка, автоматические проверки на синтетических данных, запуск настоящего окна, запись через NVENC и сравнение производительности — разные виды доказательств. Исторические `VALIDATION.md` и `UI-VALIDATION.md` описывают прошлые проверки и не заменяют проверку текущего изменения.

## 4. Приёмка и передача

Перед завершением проверьте все критерии и diff. Обновите документацию изменившегося поведения. Не переписывайте прошлые результаты новым числом без даты и условий. Для новой проверки добавляйте отдельную запись с версией или идентификатором исходников.

Для изменений программы включайте в план обязательный стабильный GitHub Release. Пользователь заранее разрешил повышение версии, коммит/push, тег и публикацию после успешных проверок; повторное подтверждение не нужно. Один push или запись нового номера в `VERSION` не завершает доставку программы.

Обновите `VERSION` и секцию `CHANGELOG.md`, соберите и проверьте соответствующие EXE и пакет. Создайте коммит только из файлов задачи и отправьте текущую ветку в `origin`. Не используйте `git add .` при посторонних изменениях; просмотрите staged diff. Выпускайте из проверенной `main`, содержащей изменения: тег `v<VERSION>` должен указывать на проверенный коммит. Не выполняйте автоматический merge или force push; при работе в другой ветке не помечайте доставку завершённой до её включения в `main` разрешённым способом.

Выполните [процесс выпуска](RELEASING.md): отправьте новый тег, дождитесь успешного workflow, проверьте опубликованный стабильный Latest-релиз, состав файлов и SHA-256 загруженных артефактов по `SHA256SUMS.txt`. Исправляйте сбои CI и публикации в текущей задаче. Если нужно менять исходники после постановки тега, используйте следующую PATCH-версию и новый тег; существующий тег не переносите. При внешней блокировке укажите точный незавершённый этап. Не выдавайте draft, артефакт Actions или зелёную сборку без опубликованного релиза за завершённую доставку.

Один релиз соответствует завершённой задаче с изменениями программы. Для чисто документационных правок достаточно проверки документов, коммита и push, если выпуск отдельно не поручен. Старые отчёты о проверках не переписывайте под новую версию: фиксируйте актуальные доказательства отдельно.

Финальный отчёт должен содержать:

1. Что изменилось и какие критерии выполнены.
2. Какие проверки фактически выполнены: команда/сценарий, код выхода, результат, ссылка на отчёт. Для ручного сценария — шаги и наблюдение.
3. Какие ошибки найдены и как подтверждено исправление.
4. Замеры ресурсов до/после либо обоснование неприменимости; непроверенные аппаратные сценарии и ограничения.
5. Ссылки на результат и план, статус коммита/push, версия и ссылка на опубликованный GitHub Release, результат CI и проверки файлов; для документационной задачи — применимость выпуска.

Не пишите «всё готово», если обязательный критерий остаётся `failed` или `blocked`. Сообщайте конкретно: реализация готова, такие-то проверки пройдены, такая-то часть не подтверждена.
