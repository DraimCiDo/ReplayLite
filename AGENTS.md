# Работа над ReplayLite

## Обязательный порядок работы

Эти правила обязательны для каждой задачи. До правок прочитайте [порядок разработки](docs/AGENT-WORKFLOW.md), [правила проверок](docs/TESTING.md) и [требования к производительности](docs/PERFORMANCE.md). Создайте план по [шаблону](docs/templates/WORK-PLAN.md). Не начинайте реализацию без плана с критериями приёмки и проверками.

1. Изучите затронутый код, ограничения среды, состояние Git и существующие проверки. Зафиксируйте исходное поведение и риски.
2. Составьте полный план: результат, границы задачи, шаги, зависимости, рабочие и ошибочные сценарии, проверка производительности, условия завершения. Выполняйте его по порядку; отмечайте фактическое состояние каждого шага.
3. При новых обстоятельствах сначала обновите план и объясните изменение. Не меняйте цель молча. Неизвестную деталь, существенно меняющую поведение, уточните у пользователя; независимую работу продолжайте.
4. Реализуйте изменение и выполните проверки на свежей сборке. Успешная сборка, наличие EXE и строка `PASS` сами по себе не доказывают работоспособность.
5. Найденный баг в затронутом поведении сразу внесите в план, воспроизведите, исправьте и повторите упавший сценарий и связанные регрессии. Не переносите известный дефект в «рекомендации» ради завершения задачи. Постороннюю проблему зафиксируйте отдельно; расширяйте объём только при необходимости для задачи.
6. Проверьте критерии приёмки и представьте доказательства: команды, коды выхода, наблюдаемый результат, артефакты и ограничения. Пропущенная или заблокированная обязательная проверка означает неполную проверку, а не успех.

## Производительность — свойство продукта

ReplayLite должен выделяться низким потреблением ресурсов ПК. Любое изменение оценивайте с учётом CPU, RAM, GPU/VRAM, диска и влияния на игру. Сохраняйте GPU-захват, аппаратный NVENC, сжатый кольцевой буфер и экспорт без перекодирования. Отступление от этих решений требует обоснования и замеров в плане.

Не добавляйте постоянный опрос, неограниченные очереди, накопление кадров в RAM, лишние процессы, копирование кадров через CPU и постоянную перерисовку без доказанной необходимости. Для изменений пути записи, экспорта, восстановления, таймеров и UI выполните применимые замеры по `docs/PERFORMANCE.md`. Измеримую регрессию исследуйте и устраните либо явно согласуйте компромисс; не объявляйте её допустимой самостоятельно. Превосходство над конкурентами подтверждайте только сопоставимым тестом.

## Завершение и сохранность

- Общайтесь с пользователем по-русски.
- После изменений программы проверьте значимое поведение, создайте коммит и отправьте текущую рабочую ветку в `origin`. Пользователь разрешил коммиты и push после изменений; повторное подтверждение не требуется.
- После каждого завершённого набора изменений программы обязательно выпускайте новую стабильную версию в GitHub Releases по [инструкции выпуска](docs/RELEASING.md). Пользователь заранее разрешил повышение версии, создание и push тега, публикацию GitHub Release после успешных проверок; повторное разрешение не требуется. Одного push в `main` или изменения `VERSION` недостаточно.
- Включайте выпуск и проверку релиза в план с самого начала. Согласуйте `VERSION`, `CHANGELOG.md`, версию EXE и тег `v<VERSION>`; дождитесь успешного release workflow. Проверьте, что релиз опубликован, не draft/prerelease, выбран как Latest и содержит установщик, Portable ZIP, EXE и корректный `SHA256SUMS.txt`. В финальном ответе дайте ссылку на релиз.
- Создавайте один релиз в конце задачи, а не для каждого промежуточного коммита. По умолчанию повышайте PATCH; если подходящая новая версия уже подготовлена и ещё не опубликована, используйте её. Не перезаписывайте опубликованные версии и теги, не публикуйте непрошедшие проверки сборки. При сбое CI или публикации исправьте причину и завершите выпуск; если мешают доступы или среда, явно укажите незавершённый этап.
- Не публикуйте непроверенный результат как завершённый. Если проверка или push не прошли, сообщите об этом явно.
- Сохраняйте чужие изменения. Не используйте force push.
- Не включайте в Git записи экрана, пользовательские настройки, временные файлы, токены и двоичные файлы сторонних зависимостей. Иконки приложения из `assets/` входят в исходники проекта.
- При изменениях интерфейса сохраняйте малый расход ресурсов: анимации должны завершаться и отключаться после скрытия окна; не добавляйте постоянную перерисовку.
- Для правок только документации проверьте ссылки, команды по исходникам, согласованность правил и diff; запуск записи и новый релиз не требуются, если пользователь отдельно не поручил выпуск. Не приписывайте этому тестирование программы.
- Если `.git` отсутствует, не подменяйте исходную историю: сообщите об ограничении; при поручении подключить репозиторий получите его существующую историю без перезаписи рабочих файлов.
